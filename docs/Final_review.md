## ส่วนที่ 1: ความสอดคล้องระหว่างเอกสารกับโค้ดจริง

1. ไล่เช็คทุกข้อใน `docs/FEATURES.md` ทีละข้อ (3.1 ถึงข้อสุดท้าย) ว่า:
   - ที่ทำเครื่องหมาย `[x]` ไว้แล้ว มีโค้ดรองรับจริงหรือไม่ (ไม่ใช่แค่ติ๊กไว้เฉยๆ)
   - มีฟีเจอร์ไหนที่ทำจริงแล้วแต่ยังไม่ได้ติ๊ก/บันทึกไว้ในเอกสารหรือไม่
2. เช็ค `docs/DATABASE.md` เทียบกับ `backend/database/schema.sql` จริง - มีตาราง/คอลัมน์ไหนที่เอกสารเขียนไว้ไม่ตรงกับ schema จริงหรือไม่ (เช่น ชื่อคอลัมน์เปลี่ยนไปแล้วแต่เอกสารไม่ได้อัปเดต)
3. เช็ค `docs/ROLES.md` เทียบกับ `roleMiddleware(...)` จริงในทุกไฟล์ `*.routes.js` - มี endpoint ไหนที่สิทธิ์ในโค้ดไม่ตรงกับที่เอกสารระบุหรือไม่

## ส่วนที่ 2: ความสอดคล้องของ Soft Delete (จุดเสี่ยงเพราะทำแยกกันคนละรอบ)

ตอนนี้มีการทำ Soft Delete ไว้ที่ `tb_news` (`is_deleted`) และ `tb_villager` (`is_deleted`) แยกกันคนละช่วงเวลา ให้เช็ค:
1. มีตารางอื่นที่ควรมี Soft Delete แต่ยังไม่มีหรือไม่ (เช่น `tb_activity`, `tb_document`, `tb_category` - ถ้าลบแล้วมี foreign key จากตารางอื่นอ้างอิงอยู่ จะพังแบบเดียวกับที่เจอมาก่อนหน้านี้หรือไม่)
2. ทุก query ที่ `SELECT` จาก `tb_news` และ `tb_villager` ทั่วทั้งระบบ (ไม่ใช่แค่ที่เคยแก้ตอนแรก) กรอง `is_deleted = 0` ครบทุกจุดหรือไม่ - ไล่เช็คทุกไฟล์ที่ `require` โมเดลทั้งสองตัวนี้

## ส่วนที่ 3: Security Checklist รวม

1. เช็คทุก endpoint ที่ไม่มี `authMiddleware` (public endpoints) - ทั้งหมดมีเหตุผลที่ควรเปิด public จริงหรือไม่ และไม่มี field ข้อมูล sensitive หลุดออกมาในแต่ละ endpoint (โดยเฉพาะ `/api/user/public/contacts`, `/api/news/public/list`, `/api/zone`)
2. เช็คทุกจุดที่รับ input จาก client แล้วเอาไปต่อ SQL string ตรงๆ (ไม่ผ่าน parameterized query) - มีหลงเหลืออยู่หรือไม่
3. เช็คทุก endpoint ที่ควรมี rate limiting (login, forgot-password, reset-password, villager send-otp) - ใช้ middleware เดียวกันครบทุกจุดหรือไม่ มีจุดไหนตกหล่นหรือไม่
4. เช็คว่า `.env.example` ล่าสุด มี key ครบตามที่โค้ดปัจจุบันเรียกใช้จริงทั้งหมดหรือไม่ (ไล่ `process.env.` ทุกจุดในโปรเจกต์เทียบกับไฟล์นี้)
5. เช็คว่ามี credential/token/API key หลุดอยู่ใน source code ที่ commit เข้า git หรือไม่ (grep หา pattern ที่ดูเหมือน API key, token ยาวๆ hardcode)

## ส่วนที่ 4: Dead Code / ความสะอาดของโค้ด

1. หาไฟล์ที่สร้างไว้แต่ไม่มีที่ไหนเรียกใช้เลย (unused files)
2. หา import ที่ import มาแต่ไม่ได้ใช้ในไฟล์นั้น
3. หา `console.log` ที่ยังหลงเหลือแบบ debug (ไม่ใช่ operation log ที่ตั้งใจเก็บไว้แบบ `[scheduler]`)
4. หา TODO/FIXME comment ที่ค้างอยู่ - อันไหนทำเสร็จแล้วแต่ลืมลบ comment อันไหนยังไม่เสร็จจริง

## ส่วนที่ 5: Environment & Deployment Readiness

1. ไล่หาทุกจุดที่โค้ด hardcode ค่าที่ควรเป็น environment variable (URL, ID, timeout values ที่ไม่ควร fix ตายตัว)
2. เช็คว่ามีจุดไหนที่โค้ดยังผูกกับ `ngrok` โดยตรง หรือ assumption ที่จะพังถ้าเปลี่ยนไปใช้ domain จริง
3. เช็ค `package.json` ทั้ง backend และ frontend - มี dependency ที่ไม่ได้ใช้แล้วค้างอยู่หรือไม่ (เพิ่มขนาด node_modules โดยไม่จำเป็น)

## ส่วนที่ 6: Database Integrity

1. เช็คว่าทุกตารางมี index ที่เหมาะสมหรือไม่ โดยเฉพาะคอลัมน์ที่ใช้ `WHERE`/`JOIN` บ่อย (เช่น `line_user_id`, `news_id` ในตาราง log ต่างๆ) - ถ้าไม่มี index ระบบจะช้าเมื่อข้อมูลเยอะขึ้น
2. เช็คว่า foreign key ทุกจุดมี `ON DELETE` behavior ที่เหมาะสม (ไม่ใช่ CASCADE ตามที่ตัดสินใจไว้แล้ว แต่ต้องไม่ใช่ error แบบไม่คาดคิดในจุดอื่นที่ยังไม่เคยเจอ)
3. เช็คว่ามีตารางไหนที่ข้อมูลจะโตไม่มีที่สิ้นสุดโดยไม่มีการจัดการหรือไม่ (เช่น `tb_view_log`, `tb_chat_log` - ควรมีแผน archive/cleanup ในอนาคตหรือไม่ แค่รายงานไว้ ไม่ต้องแก้ตอนนี้)

## ส่วนที่ 7: สรุปภาพรวมสุดท้าย

1. สรุปเป็นตาราง: ฟีเจอร์ทั้งหมดในระบบ, สถานะ (เสร็จสมบูรณ์ / เสร็จแต่มีข้อจำกัด / ยังไม่ทำ), พร้อมข้อจำกัดที่ควรรู้ก่อนนำเสนอ (ถ้ามี)
2. สรุปรายการ "ข้อจำกัดที่ควรเตรียมตอบกรรมการ" ถ้าถูกถาม (เช่น ยังไม่ deploy จริง, ยังไม่มี automated backup, ระบบยังไม่รองรับหลายหมู่บ้านพร้อมกัน)
3. ให้คะแนนความพร้อม (1-10) แยกตามหมวด: Backend completeness, Frontend completeness, Security, Documentation, Testing coverage พร้อมเหตุผลสั้นๆ ของแต่ละคะแนน
